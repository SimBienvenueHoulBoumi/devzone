# internal/command

- Role: receives the devzone command line; runs in Go the commands of the `ported` table, delegates the others to the bash bridge (#358).
- May import: the standard library, `internal/bashbridge` and `internal/workspace`.
- Must not import: `cmd/...` (the binary depends on this package, never the reverse) nor a business package that would depend on bash.
- The `ported` table lists the ported commands: `--version`, `-v`, `help`, `-h`, `--help`, only alone, with no other argument; and `workspace`, for the `status`, `stop`, `vscode` and `shell` sub-commands only (#712), for `copy-to` and `copy-from` with one folder argument (#754), and for `clone` with a url and an optional name (#754): `workspaceCommand` in `workspace.go`. A command enters it when it is ported, and leaves the delegation in the same change. `devzone workspace` followed by anything else (another sub-command, or one of these followed by a word) stays delegated to bash. `workspace stop` is delegated too when Argo CD holds the workspace (see `internal/workspace/README.md`). `workspace shell` receives the terminal of the user as standard input. `ports start`, `ports loop` and `ports agent` run in Go on Windows too (#883): the watcher has real process primitives there. Its automatic start is in Go on Windows too (#903): `ports enable|disable` create and delete a user task through `schtasks`, and the automatic-start gate no longer refuses Windows. `workspace services enable|disable|seed` run in Go for the forms that do not need Argo CD, `start` runs in Go when Argo CD is off and absent, `update` runs in Go with the release resolution, the registry check and the deploy/reconcile callbacks, `egress` and the internal `egress params` run in Go with the settings and the redeploy at the running image, and `argocd` and `argocd status` run in Go with the shared `.argocd.conf` reader; the other forms stay delegated to bash until the GitOps libraries are ported.
- `host-check <command name>` is internal (not in the help): the shell scripts that still run (`manage/scripts/uninstall.sh`) call it through `DEVZONE_HOST_BIN`, exported by `manage/devzone`, for the host engine check of `internal/platform/hostcheck` (#884). Its tests use a fake runner.
- `cluster-offer` is internal too: the former `manage/scripts/create-mode.sh` called it when no cluster answered at creation, for the menu of `internal/platform/clustermenu` (#884); the decision now calls that menu in Go. Status 0 once a cluster was selected or created, 1 otherwise or without a terminal (`DEVZONE_TERMINAL` or a real terminal on stdin). Its tests use a fake runner, and fake standard inputs.
- `kube-ready [--hint]` is internal: the shell callers use it through `DEVZONE_HOST_BIN` instead of sourcing the former shared script (#884). The reason goes to stdout and status 0 means the cluster answers. Its tests use a fake runner and a fake program lookup.
- `create-mode` is internal too (#884): `choose`, `write` and `start`, the decision of `internal/platform/createmode`; `choose` prints only the mode on stdout, notices go to stderr, and its tests use a fake runner and lookup. `create-workstation` calls the three in-process.
- `create-workstation` is internal too: the bash caller makes a single call with the folder name first, then `--gitops`/`--kubernetes`, instead of sourcing the former `devzone-create.sh` (#884). Creation lives in `internal/platform/create`; its tests use a fake runner.
- Tests: `go test ./internal/command/`; the delegation tests use a fake bash entry point, those of `workspace status`, `stop`, `vscode`, `shell`, `copy-from` and `clone` a fake `kubectl` (and a fake `helm`) in the PATH.
